# Продукт и правила Clutch

Статус: подтверждённые решения владельца + отдельно помеченные предложения.
Основа — checkpoint `e110d5c`; состояние дополнено R5c в рабочем дереве 2026-10-01.

## Основная задача

Дать короткое соревнование, где знания открывают попытку, а точность действия
определяет результат. Основной экран — телефон в Telegram; язык интерфейса —
русский. Контент и challenges можно связывать с короткими видео владельца.
Это не только викторина и не симулятор забивания гвоздя.

```text
Категория → сохранённый соперник / бот → вопрос → разбор ответа
                                                    ↓
                                    верно: skill-попытка
                                    неверно: без попытки
                                                    ↓
                              прогресс обоих → следующий вопрос / итог
                                                    ↓
                                 сохранение прохождения для будущих матчей
```

## Подтверждённые решения

- Матчмейкинг отложенный, не live: игрок B получает запись игрока A и тот же
  набор вопросов. Синхронное подключение A не требуется.
- Общий HUD не зависит от мини-игры: имена, проценты, progress bars, номер раунда.
  Гвоздь/пень/молоток находятся только в сцене Hammer the Nail; будущая игра
  должна менять свою сцену, а не экран вопросов.
- Визуальные прототипы и нынешняя анимация не являются релизным качеством.
  Сначала выбирается согласованный стиль, потом производится комплект ассетов.
- Локальный backend и запуск Mini App через HTTPS-туннель нужны для разработки.

## Текущие правила прототипа

| Область | Поведение в коде |
| --- | --- |
| Набор | Обычный матч — 10 вопросов, challenge Robb — 9; возможен ранний финиш |
| Вопрос | 15 секунд; выбор варианта либо открытый ввод с fuzzy matching |
| Категории | География; исторические флаги (`history`); языки |
| Награды | perfect 25, great 18, good 12, weak 5, miss 0 |
| Pressure | Stage 0..3 равен числу прошлых non-miss skill results с cap 3; miss и неверный ответ stage не повышают |
| Зоны skill | Базовые пороги 0.15 / 0.35 / 0.65 / 0.85 умножаются на 1 / 0.9 / 0.8 / 0.7; target детерминирован из question id |
| Прогресс | Сумма наград, ограниченная 100% |
| Завершение | Любой достиг 100%, либо сыгран последний вопрос |
| Победитель | Сравнение процентов; одинаковые проценты дают ничью |
| Соперник | Его награда применяется после текущего раунда игрока |
| Профиль | Локальная статистика устройства, не серверный аккаунт |

Это описание реализации. Фраза «первый до 100%» сейчас не означает сравнение
реального времени: если оба набрали 100% в одном раунде, получается ничья.

## DEC-01 — ранний финиш и полноценность записи: выбран вариант 1

Исходная проблема до R1b: A проигрывает на шестом вопросе, когда соперник достигает 100%.
В D1 сохраняются шесть результатов A и набор из десяти вопросов. B получает A
как соперника; на вопросах 7–10 у A больше нет результатов. Код трактует их как
нулевой прогресс, хотя A эти вопросы не играл.

Возможные правила:

1. **Сохранить гонку до 100%.** Разделить «матч завершён» и «запись пригодна
   для пула»: полный набор либо собственное достижение 100% — кандидат в пул;
   досрочное поражение — история игрока, но не полноценный ghost. Нужны
   проверки порядка, терминального раунда и версии правил.
   Минус: меньше записей в пуле, возможен перекос к сильным прохождениям.
2. **Всегда проходить десять вопросов.** Запись независима от раннего успеха
   соперника. Потребуется другая итоговая шкала или тай-брейк: ограничение 100%
   при полном прохождении даст много одинаковых результатов.

После согласия владельца продолжить 2026-09-27 для R1 принят вариант 1:
гонка до 100% сохраняется, завершение матча отделено от пригодности ghost.
Реализация выполнена поэтапно: shared-правила → API/хранение → клиент.
После миграции 0002 сервер и клиент применяют одинаковые переходы; клиент также
проверяет версию условий и нормализует только явно локальные scripts.

| Законное состояние прохождения | Завершён? | Кандидат в пул? |
| --- | --- | --- |
| Неполный набор, обе стороны ниже 100% | Нет | Нет |
| Игрок сам достиг 100%, в том числе одновременно с соперником | Да | Да |
| Раннее поражение, игрок ниже 100% | Да | Нет |
| Сыгран весь набор без более раннего финиша | Да | Да, независимо от победы |

После первого терминального раунда дополнительные раунды недопустимы.
Пригодность по этим правилам — только один фильтр: совместимость версий,
авторизация и проверка входных данных остаются задачами API.

## Ничья и остальные продуктовые решения

- **DEC-02 — ничья и время: для R1 оставляем ничью.** Исход определяется по
  ограниченным 100% значениям на границе раунда; одинаковые значения дают ничью,
  включая одновременные 100%. Тайминг ответов не используется как тай-брейк.
  Это сохраняет поведение прототипа, а не вводит новое соревнование на скорость.
- **DEC-03 — режим доверия:** частный casual-прототип или публичное соревнование
  с рейтингом? Авторизация обязательна для публичного сохранения в любом случае;
  глубина античита зависит от выбранного режима. Рекомендация: сначала casual,
  без обещания защищённого рейтинга или призов. R5c заставляет клиент и API
  одинаково пересчитывать pressure-tier из distance, но distance по-прежнему
  сообщает клиент; это согласование правил, не античит.
- **DEC-04 — прогресс гвоздя:** показывать качество отдельного удара, как сейчас,
  или накопленную глубину за матч? Рекомендация — накопленный прогресс внутри
  мини-игры и отдельная обратная связь за удар. Утвердить до финальных спрайтов.
  R5c не вводит накопленную глубину и не означает одобрения этого предложения.
- **DEC-05 — оформление:** стиль и провайдер не выбраны. Варианты и критерии —
  [ART_DIRECTION.md](ART_DIRECTION.md).

## Ближайшая цель и границы

Рекомендованная цель: один законченный async-сценарий, который приятно пройти
на телефоне и чей результат действительно сохраняется и повторяется другим
игроком на сопоставимых условиях. Это следующий этап, не достигнутый статус.

До расширения проверить: понимание правил без объяснений, повторную игру,
долю успешных сохранений, долю реальных ghost, причины выходов/ошибок. Числовые
целевые показатели ещё не установлены; аналитика пока не собирает их на сервере.

Вне рекомендуемого ближайшего этапа: live PvP, WebSockets, сложный рейтинг,
монетизация, CMS, массовое производство арта, новая мини-игра и новые категории.
Они не нужны, чтобы проверить основной замысел.
