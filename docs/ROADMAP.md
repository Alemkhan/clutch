## R2 · Владение матчем и ограничения входа

Основание: A01, A06. Модель: 5.6-Sol, medium.
Файлы: API, web `lib/api.ts`, shared request-типы, интеграционные тесты.

- **R2a — выполнено 2026-09-30.** Telegram identity выводится из проверенного
  initData на каждом запросе; браузер получает подписанную guest-сессию и
  продлевает тот же subject. Start не принимает playerId, а complete проверяет
  владельца до выдачи сохранённого результата. Чужой/отсутствующий id дают 404.
- **R2b — выполнено 2026-09-30.** JSON start/complete ограничен 1024/16384
  байтами до разбора; completion принимает 1..10 раундов, `questionId` 1..128,
  `selectedAnswer` 0..512 символов и `responseTimeMs` 0..60000. Нативный binding
  ограничивает guest/start/complete/leaderboard до 30 запросов за 60 секунд в
  раздельных bucket. Binding error закрывается 503, превышение — 429 с
  `Retry-After: 60`.
- Для R2a готовы тесты отсутствующей/поддельной identity, чужого matchId,
  истёкшего initData и законного повтора. R2b покрыт отдельными тестами байтов,
  структуры, всех четырёх ключей rate limit и отказа binding.
- Не добавлять полноценную регистрацию и не называть это завершённым античитом.
  Выбор защиты scoring/скрытия ответов делается отдельно после DEC-03.

## R3 · Подтверждение и повторная отправка результата

Основание: A03. Модель: 5.6-Sol, medium. Зависимость: стабильный контракт R1/R2.

- **R3a: серверная часть выполнена вместе с R1b.** Completion проверяет результат
  conditional UPDATE и возвращает сохранённую запись при проигранной гонке.
  Повтор и два конкурентных payload проверены route-тестами; клиентский контур
  поверх этой идемпотентности добавлен в R3b/R3c.
- **R3b — выполнено 2026-09-30.** Versioned localStorage-очередь до 20 записей,
  canonical payload без auth token, single-flight, bootstrap/online flush и до
  четырёх transient-попыток с 1/3/10 с либо `Retry-After`. Terminal 4xx и
  некорректный ACK остаются видимой ошибкой без retry; exhausted transient
  допускает ручной новый цикл. Pending/saved/error/practice показаны на итоге.
- **R3c — выполнено 2026-09-30.** ACK принимается только для того же matchId и
  после runtime-проверки; UI сверяет server progress/correct/rounds. Отдельная
  confirmed-online статистика выводит outcome из server progress и сохранённого
  opponent snapshot, дедуплицируется по matchId и не импортирует legacy practice.
- Файлы: API complete, web `api.ts`, `useGameState.ts`, `localStats.ts`,
  `ResultScreen.tsx`; отдельный модуль очереди при необходимости.
- Покрыто unit-тестами: persistence/reload, timeout→ACK, terminal 4xx, exhaustion
  и manual retry, single-flight, malformed/wrong-match ACK, Retry-After и dedup.
  Реальный browser offline/reload и Telegram остаются ручной проверкой.
- Восстановление незаконченного матча — отдельная следующая задача, не скрытое
  расширение очереди завершённых результатов.

Основание: A04. Модель: 5.6-Sol, low/medium.
