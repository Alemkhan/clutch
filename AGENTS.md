## Разделение работы по моделям

Предпочтение владельца от 2026-09-27:

- Astra — анализ, архитектура, продуктовые решения, ревью и контекстные документы.
- Реализация кода — более лёгкая модель, например **5.6-Sol**, с низким reasoning
  для локальных правок и средним для задач через несколько слоёв.
- Перед реализацией подготовь ограниченный brief: цель, файлы, исключения,
  критерии готовности, проверки. Используй задачи из ROADMAP.
- Если доступна делегация и пользователь попросил реализацию, передавай кодинг
  такой модели; не запускай дополнительный аудит сабагентами без необходимости.
  Если переключение недоступно, сообщи об этом, не утверждай, что сменил модель.
- Не увеличивай reasoning и число агентов автоматически. Проверка результата
  и тесты обязательны независимо от модели.

## Продуктовые ограничения

- Это русскоязычная mobile-first Telegram Mini App, также работающая в браузере.
- Матчмейкинг **асинхронный**: игрок соревнуется с сохранённым прохождением.
  Live PvP, WebSockets и присутствие второго игрока сейчас не нужны.
- Общий Match HUD показывает личности, проценты и полосы прогресса. Гвозди,
  молотки, мишени и другая тематическая графика принадлежат только мини-играм.
- Правильный ответ даёт попытку в мини-игре; качество попытки даёт прогресс.
- Старые спрайты — отклонённый прототип, не утверждённый визуальный стиль.
- Не выдавай бота за запись человека, локальный результат за сохранённый,
  а предложенное правило за утверждённое. Ошибки текущего кода — не требования.

## Границы изменений и проверка

- При запросе анализа не исправляй код приложения самовольно. Документация
  разрешена, когда её просит пользователь. Не делай commit/push/deploy без запроса.
- Сохраняй чужие незакоммиченные изменения. Не читай и не выводи секреты из
  `.dev.vars`, `.env` и аналогичных файлов; используй шаблоны окружения.
- Изменения D1 оформляй новой миграцией; не переписывай применённую миграцию.
  История 0001–0017 сжата в единственный `0001_schema.sql` 2026-10-13 — это было
  возможно только потому, что на remote не разворачивали ничего ни разу, а
  локальная база была пуста. После первого деплоя так делать нельзя.
- Не начинай общий рефакторинг, замену стека или новую мини-игру внутри небольшой
  задачи. Не меняй награды и условия победы под видом исправления анимации.
- Для кода: целевые регрессионные тесты, `npm test`, `npm run build`.
  Для документации: проверка ссылок и `git diff --check`.
- Для UI дополнительно проверяй маленький экран, открытый ввод/клавиатуру,
  длинный текст, загрузку/ошибку и reduced motion. Браузерная эмуляция не заменяет
  проверку в Telegram на настоящем телефоне.
- После задачи обнови только затронутую часть контекста. Указывай, что реально
  проверено, а что остаётся гипотезой или ручной проверкой.
